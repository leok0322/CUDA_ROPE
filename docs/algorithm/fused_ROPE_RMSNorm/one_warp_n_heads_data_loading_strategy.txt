================================================================================
一个 warp 处理 N 个 heads 的 Fused QKNorm + RoPE 数据加载策略：寄存器、SMEM 与 cp.async 流水
================================================================================

章节导航：
  一、数据的复用粒度
  二、为什么 dynamic SMEM 大小按 block 的最坏情况确定
  三、QKV + cos/sin + q_weight/k_weight 联合加载策略
  四、推荐的执行流水
  五、一个 block 处理一个 token 的替代流水
  六、常见错误
  七、速查表


核心一句话：
  · 本文讨论的是一个 warp 连续处理同一个 token 的 N 个 Q/K heads 时，QKV、cos/sin、
    q_weight/k_weight 应该如何加载、复用和流水化。
  · QKV 是每个 token/head 独有的数据；如果要隐藏 QKV global load 延迟，核心手段是
    QKV 双缓冲 cp.async。
  · cos/sin 和 q_weight/k_weight 都是小的只读数据，都会被同一个 warp 的多个 head 复用；
    它们放寄存器还是 SMEM 不是理论上绝对确定的结论，而是资源取舍和 benchmark 问题。
  · 本文把主要候选方案收敛为三类：方案 1：QKV 双缓冲 + cos/sin SMEM + q/k weight 寄存器；
    方案 2：QKV 双缓冲 + cos/sin/q/k weight 寄存器；方案 3：QKV 双缓冲 + cos/sin/q/k weight
    都异步进入 SMEM。


================================================================================
一、数据的复用粒度
================================================================================

  fused QKNorm + RoPE 里主要有三类输入：

    1. qkv
       · 形状通常可理解为 [num_tokens, (num_heads_q + num_heads_k + num_heads_v) * head_dim]。
       · Q/K head 会被就地归一化并做 RoPE。
       · 每个 warp 负责同一个 token 的若干个 Q/K head。
       · 每个 head 的 QKV 数据不同，不能跨 head 复用。

    2. cos/sin
       · 形状通常可理解为 [num_tokens, rotary_dim / 2]，或 cos/sin 合并缓存
         [num_tokens, rotary_dim]。
       · 同一个 token 的所有 head 使用同一份 cos/sin。
       · 如果一个 warp 处理同一个 token 的多个 head，那么 cos/sin 可以在这些 head 间复用。

    3. q_weight/k_weight
       · 形状通常是 [head_dim]。
       · 它们是 Q/K RMSNorm 的权重。
       · 不随 token 变化，也不随 head 变化。
       · 一个 warp 处理多个 head 时，q_weight/k_weight 可以在这些 head 间复用。


================================================================================
二、为什么 dynamic SMEM 大小按 block 的最坏情况确定
================================================================================

  dynamic shared memory 的大小由 kernel launch 第三个参数指定：

    kernel<<<gridDim, blockDim, dynamic_smem_bytes>>>(...);

  这个大小对所有 block 相同，不能在 kernel 内根据“当前 block 实际处理几个 token”
  动态改变。

  因此 dynamic_smem_bytes 应该按每个 block 实际使用到的 SMEM 缓冲计算：

    warpsPerBlock = blockDim.x / 32

    dynamic_smem_bytes =
        必需/启用的 cos/sin 空间
      + 可选的 QKV tile / 双缓冲空间
      + 可选的 q/k weight 缓存空间
      + 必要的对齐 padding

  当前多 head/warp 映射下，一个 block 里的不同 warp 可能处理不同 token：

    globalWarpIdx  = blockIdx.x * warpsPerBlock + warpIdxPerBlock
    tokenIdx       = globalWarpIdx / warpNumPerToken
    warpIdxInToken = globalWarpIdx % warpNumPerToken

  所以不能假设一个 block 只对应一个 token。


================================================================================
三、QKV + cos/sin + q_weight/k_weight 联合加载策略
================================================================================

  QKV、cos/sin、q_weight/k_weight 不应该分成孤立问题看。它们进入同一个 per-warp
  head 循环：

    · QKV：每个 head 独有，通常只被当前 lane 使用一次，天然复用弱。
    · cos/sin：和 token 绑定，同一个 warp 处理多个 head 时可以复用。
    · q_weight/k_weight：和 dim 绑定，不随 token/head 变化，同一个 warp 处理多个 head
      时也可以复用。
    · QK RMSNorm：依赖 QKV 和 q_weight/k_weight。
    · RoPE：依赖 RMSNorm 后的 Q/K 和 cos/sin。

  因此不能简单说“cos/sin 适合 SMEM，q_weight/k_weight 适合寄存器”。二者有很多相同点：

    · 都是小的只读数据。
    · 都会被同一个 warp 的多个 head 复用。
    · 最终都要进入寄存器参与计算。
    · 如果先放 SMEM，都会多一次 SMEM -> register 的读取。
    · 如果长期放寄存器，都会增加跨 head 循环的寄存器 live range。

  真正要比较的是三条执行路径：

    方案 1：
      QKV async 双缓冲到 per-warp SMEM；
      cos/sin async 到 per-warp SMEM；
      q_weight/k_weight 同步加载到寄存器。

    方案 2：
      QKV async 双缓冲到 per-warp SMEM；
      cos/sin 同步加载到寄存器；
      q_weight/k_weight 同步加载到寄存器。

    方案 3：
      QKV async 双缓冲到 per-warp SMEM；
      cos/sin async 到 per-warp SMEM；
      q_weight/k_weight async 到 per-warp SMEM。

  这三种方案都成立，区别不是“谁理论上一定正确”，而是：

    · 寄存器占用是否过高。
    · SMEM 占用是否影响 occupancy。
    · cp.async 能否真正和计算重叠。
    · 多出来的 SMEM -> register 读取是否被复用收益和延迟隐藏抵消。
    · q_weight/k_weight、cos/sin 是否已经被 L1/L2/read-only cache 很好地缓存。


--------------------------------------------------------------------------------
  共同地址约定
--------------------------------------------------------------------------------

  如果 cos/sin 分开存储：

    cos: [num_tokens, rotary_dim / 2]
    sin: [num_tokens, rotary_dim / 2]

  可以把它们连续放进当前 warp 的 cos/sin SMEM：

    [0, rotary_dim / 2 * sizeof(T_cache))
        cos

    [rotary_dim / 2 * sizeof(T_cache), rotary_dim * sizeof(T_cache))
        sin

  访问指针：

    T_cache* warp_cache =
        reinterpret_cast<T_cache*>(this_warp_cos_sin);

    T_cache* cos_smem = warp_cache;
    T_cache* sin_smem = warp_cache + rotary_dim / 2;

  如果用 cp.async 16B 版本搬 cos/sin，最好保证拷贝总字节数是 16 的倍数，或者显式处理
  尾部边界，避免最后一笔 16B 拷贝越界写 SMEM。

  q_weight/k_weight 的 per-lane 访问通常是：

    q_weight: [head_dim]
    k_weight: [head_dim]

    dim = laneIdx * elementNumPerHeadPerThread + i

  cos/sin 的 per-lane 访问通常是：

    half_dim = (laneIdx * elementNumPerHeadPerThread + 2 * i) / 2

  如果只看当前 warp 处理同一个 token 的多个 head，二者都可以在 head 循环外加载一次，
  然后跨多个 head 复用。不同策略的核心差异在于：这份复用数据是长期放在寄存器，还是
  放在 SMEM 中、每个 head 使用时再短生命周期读入寄存器。


--------------------------------------------------------------------------------
  方案 1：QKV 双缓冲 + cos/sin SMEM + q_weight/k_weight 寄存器
--------------------------------------------------------------------------------

  数据路径：

    QKV               global -> qkv_buf0/qkv_buf1 -> register
    cos/sin           global -> per-warp SMEM -> register
    q_weight/k_weight global/read-only cache -> register

  这个方案对应之前文档里的“QKV 双缓冲 + cos/sin 异步进 SMEM + q/k weight 预加载寄存器”。
  它不是理论上必然最优，而是一个折中候选：

    · QKV 用双缓冲 cp.async 隐藏 next head 的 global load 延迟。
    · cos/sin 用 cp.async 进入 SMEM，尝试和第一个 head 的 RMSNorm 重叠。
    · q_weight/k_weight 直接放寄存器，避免 q/k weight 的 SMEM 中转。

  伪代码形态：

    char* qkv_buf0 = this_warp_qkv;
    char* qkv_buf1 = this_warp_qkv + qkv_tile_bytes_per_head;

    cp_async_qkv_head(0, qkv_buf0);
    cp_async_commit_group();  // group0: head0 QKV

    cp_async_cos_sin_to_smem(this_warp_cos_sin, tokenIdx);
    cp_async_commit_group();  // group1: cos/sin

    // q/k weight 是同步 global/read-only load。放在 cp.async 之后做，
    // 可以让这部分寄存器加载和前面的异步搬运在时间上部分重叠。
    float q_w[elementNumPerHeadPerThread];
    float k_w[elementNumPerHeadPerThread];

    #pragma unroll
    for (uint i = 0; i < elementNumPerHeadPerThread; ++i) {
      uint dim = laneIdx * elementNumPerHeadPerThread + i;
      q_w[i] = convert(q_weight[dim]);
      k_w[i] = convert(k_weight[dim]);
    }

    cp_async_wait_group<1>();  // head0 QKV 完成，允许较新的 cos/sin 仍在途。
    __syncwarp();

    for (uint k = 0; k < headNumInWarp; ++k) {
      uint next = k + 1;

      if (next < headNumInWarp) {
        char* next_qkv_buf = (next & 1) ? qkv_buf1 : qkv_buf0;
        cp_async_qkv_head(next, next_qkv_buf);
        cp_async_commit_group();
      }

      char* cur_qkv_buf = (k & 1) ? qkv_buf1 : qkv_buf0;
      vec_T qkv_vec = load_qkv_from_smem(cur_qkv_buf);

      // RMSNorm 使用寄存器里的 q_w/k_w；这段计算可以覆盖 cos/sin 剩余加载延迟
      // 和 next head QKV 的加载延迟。
      compute_qknorm(qkv_vec, q_w, k_w, elements);

      if (k == 0) {
        if (next < headNumInWarp) {
          cp_async_wait_group<1>();  // 等较老的 cos/sin，允许最新 next QKV 仍在途。
        } else {
          cp_async_wait_group<0>();
        }
        __syncwarp();
      }

      apply_rope_from_smem_cos_sin(elements, cos_smem, sin_smem);
      store_back_qkv(k, elements);

      if (next < headNumInWarp) {
        cp_async_wait_group<0>();  // 下一轮读 next QKV 前保证它到位。
        __syncwarp();
      }
    }

  优点：

    · cos/sin 不占长期寄存器，适合 rotary_dim 较大或寄存器压力较高的情况。
    · q/k weight 不走 SMEM，少一次 q/k weight 的 SMEM -> register。
    · 可以利用 QK RMSNorm 覆盖 cos/sin 和 next QKV 的一部分加载延迟。

  代价：

    · cos/sin 仍然要从 SMEM 读回寄存器参与 RoPE。
    · 需要 per-warp cos/sin SMEM 和两个 QKV SMEM buffer。
    · cp.async group 顺序和 wait_group 安排更复杂。


--------------------------------------------------------------------------------
  方案 2：QKV 双缓冲 + cos/sin 寄存器 + q_weight/k_weight 寄存器
--------------------------------------------------------------------------------

  数据路径：

    QKV               global -> qkv_buf0/qkv_buf1 -> register
    cos/sin           global/read-only cache -> register
    q_weight/k_weight global/read-only cache -> register

  这个方案承认 cos/sin 和 q/k weight 的相同点：如果它们都能被当前 lane 在寄存器中跨
  多个 head 复用，并且寄存器压力可接受，那么 cos/sin 直接进寄存器可以省掉 SMEM 中转。
  当前 src/kernels/4_fused_QKNorm_ROPE_NHeads_kernel.cuh 的 algorithm 0 就是在向这个
  方案实现：

    · QKV 使用 cp.async global -> shared，按 current/next 两个 SMEM channel 双缓冲。
    · cos/sin 在 head 循环外从 global/read-only cache 加载到当前线程寄存器。
    · q_weight/k_weight 在 head 循环外向量化加载到当前线程寄存器，并被多个 head 复用。
    · head 循环中只复用 QKV SMEM buffer，不再为 cos/sin 或 q/k weight 分配 SMEM。

  动态 SMEM 大小也按这个实现收敛为：

    HeadsNumPerWarpSMEM = 2

    dynamic_smem_bytes =
        warpsPerBlock
      * 32
      * HeadsNumPerWarpSMEM
      * elementBytesPerHeadPerThread

  这里的 2 不是 HEADS_PER_WARP，而是 current/next 两个 QKV buffer。一个 warp 逻辑上
  可以处理 HEADS_PER_WARP 个 head，但不需要把所有 head 的 QKV 同时放进 SMEM。

  伪代码形态：

    // 1. head 循环外：cos/sin 进寄存器。
    //    当前实现不一定声明 float 数组，而是按 T_cache_tran packed 类型保存。
    //    如果一个 lane 完全不在 rotary_dim 范围内，可以不加载；后续 RoPE 分支也不会使用。
    if (cosSinNumPerHeadPerThread * laneIdx < rotary_dim / 2) {
      elementCos = load_packed_or_scalar_cos(tokenIdx, laneIdx);
      elementSin = load_packed_or_scalar_sin(tokenIdx, laneIdx);
    }

    // 2. head 循环外：q/k weight 进寄存器。
    //    当前实现用 T_in_tran 一次向量化加载，然后在 RMSNorm 循环中按 T_in 拆出标量。
    elementQWeight = vector_load(q_weight + laneIdx * elementNumPerHeadPerThread);
    elementKWeight = vector_load(k_weight + laneIdx * elementNumPerHeadPerThread);

    // 3. 先预取 head0 QKV 到 channel0。
    cp_async_qkv_head(0, qkv_channel[0]);
    cp_async_commit_group();

    for (uint k = 0; k < headNumInWarp; ++k) {
      // 当前 head 要先等它对应的 cp.async group 完成。
      // k=0 等初始化时发出的 head0；k>0 等上一轮预取的 head k。
      cp_async_wait_group<0>();

      uint currentHead = firstHeadIdx + k;
      bool currentIsQ = currentHead < num_heads_q;

      // 4. 尽早预取 next head，让 next QKV global load 和 current head 计算重叠。
      if (k + 1 < headNumInWarp) {
        uint nextChannel = (k + 1) % 2;
        cp_async_qkv_head(k + 1, qkv_channel[nextChannel]);
        cp_async_commit_group();
      }

      // 5. current head 从 current channel 读取。
      uint currentChannel = k % 2;
      load_current_qkv_from_smem(qkv_channel[currentChannel], elementPerHeadPerThread);

      // 6. RMSNorm：按 currentIsQ 选择 q_weight 或 k_weight。
      //    注意不能用 next head 的 isQ 覆盖 currentIsQ。
      compute_qknorm(elementPerHeadPerThread,
                     currentIsQ ? elementQWeight : elementKWeight);

      // 7. RoPE：使用 head 循环外加载到寄存器的 elementCos/elementSin。
      if (cosSinNumPerHeadPerThread * laneIdx < rotary_dim / 2) {
        apply_rope_from_register_cos_sin(elementPerHeadPerThread,
                                         elementCos,
                                         elementSin);
      }

      // 8. 普通 global store 写回 current head。
      //    写回不需要等 next QKV 预取完成；下一轮循环开头 wait_group<0> 再保证 next QKV 到位。
      store_back_qkv(currentHead, elementPerHeadPerThread);
    }

  与代码对应的几个关键点：

    1. cos/sin 的寄存器类型不是固定 float 数组。
       当前实现先计算：

         cosSinNumPerHeadPerThread   = elementNumPerHeadPerThread / 2
         cosSinBytesPerHeadPerThread = cosSinNumPerHeadPerThread * sizeof(T_cache)

       如果是最小半精度标量场景，就用 T_cache 标量；否则用 float/float2/float4
       作为 packed 读取类型。这样可以覆盖 2B 标量和 4B/8B/16B 向量化读取。

    2. q_weight/k_weight 一次性向量化加载。
       当前实现是：

         elementQWeight =
           reinterpret_cast<const T_in_tran*>(
             &q_weight[elementNumPerHeadPerThread * laneIdx])[0]

         elementKWeight =
           reinterpret_cast<const T_in_tran*>(
             &k_weight[elementNumPerHeadPerThread * laneIdx])[0]

       RMSNorm 内再把 elementQWeight/elementKWeight 按 T_in* 拆成每个元素的 weight。
       这种“对 packed 寄存器临时量取地址再拆包”的写法通常会被 nvcc 优化成寄存器内切片，
       但不是 C++ 语义保证，最终仍要看 PTX/SASS 或 ptxas -v 是否出现 local memory spill。

       当前 sm_86 编译结果给出的证据是：algorithm 0 的 NHeads kernel 多个实例均显示：

         0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads

       这说明当前代码形态下，对 elementQWeight/elementKWeight 取地址拆包没有导致
       local memory spill。对应 register 用量大致是：

         head_dim=64   : 32~36 registers/thread
         head_dim=128  : 34~36 registers/thread
         head_dim=256  : 56 registers/thread

       因此当前证据支持：

         · 没有寄存器溢出到 local memory。
         · 对 packed 局部变量取地址被编译器优化成了寄存器内切片/搬移。
         · head_dim=256 的寄存器压力更高，但仍然没有 spill。

       这不是永久保证。如果后续增加临时变量、扩大 live range、加入更多流水状态或改变
       编译选项，仍应重新检查 ptxas 输出中的 spill stores / spill loads。

       写回阶段的 elementT_tranPerThreadStore 也是同类问题：

         T_in_tran elementT_tranPerThreadStore;
         reinterpret_cast<T_in2*>(&elementT_tranPerThreadStore)[j] = ...

       当前同一份 ptxas 输出也显示 0 bytes stack frame / 0 spill stores / 0 spill loads，
       因此当前写回组包没有落到 local memory。

    3. cp.async 不使用 T_in_tran。
       QKV 预取只需要 global 地址、shared 地址和拷贝宽度。拷贝宽度来自
       elementBytesPerHeadPerThread，只允许 4B/8B/16B。T_in_tran 主要用于普通向量化
       load/store 或 packed 寄存器表示。

    4. 当前实现通常不需要额外 __syncwarp()。
       每个 lane 只读取自己通过 cp.async 写入的 SMEM 地址：

         qkv_smem[warp][channel][lane][element]

       不存在 lane A 写入、lane B 读取的 shared memory 依赖。cp_async_wait_group<0>()
       已经保证“当前线程自己发出的 cp.async”完成。如果后续改成跨 lane 消费 SMEM tile，
       或者不同 lane 之间存在生产/消费关系，就需要在 wait_group 后加 __syncwarp()。

  QKV 双缓冲 SMEM layout 与 bank conflict：

    方案 2 虽然把 cos/sin 和 q/k weight 放在寄存器中，但 QKV 仍然需要两个 per-warp
    SMEM buffer，用来做 current/next head 的双缓冲。每个 warp 只需要保存两个 head
    slot，而不是保存 HEADS_PER_WARP 个 head：

      HeadsNumPerWarpSMEM = 2

    推荐把 QKV SMEM 切成：

      [warp][buffer][lane][element]

    对应元素 offset：

      offset =
          warpIdxPerBlock * HeadsNumPerWarpSMEM * 32 * elementNumPerHeadPerThread
        + bufferIdx       * 32 * elementNumPerHeadPerThread
        + laneIdx         * elementNumPerHeadPerThread
        + elementIdx

    当前代码中：

      currentChannel = k % 2
      nextChannel    = (k + 1) % 2

      current head 读取:

        smem_base[
            warpIdxPerBlock * 32 * HeadsNumPerWarpSMEM * elementNumPerHeadPerThread
          + currentChannel  * 32 * elementNumPerHeadPerThread
          + laneIdx         * elementNumPerHeadPerThread
          + elementIdx]

      next head 预取:

        smem_base[
            warpIdxPerBlock * 32 * HeadsNumPerWarpSMEM * elementNumPerHeadPerThread
          + nextChannel     * 32 * elementNumPerHeadPerThread
          + laneIdx         * elementNumPerHeadPerThread]

    含义：

      · warp 维度：block 内每个 warp 有自己的 QKV 双缓冲区域。
      · buffer 维度：0/1 两个 slot，对应 current/next head。
      · lane 维度：同一个 head 内 32 个 lane 各自保存自己负责的连续元素。
      · element 维度：当前 lane 负责的 elementNumPerHeadPerThread 个 QKV 元素。

    不推荐把 buffer 放在 lane 后面：

      [warp][lane][buffer][element]

    对应元素 offset：

      offset =
          warpIdxPerBlock * 32 * HeadsNumPerWarpSMEM * elementNumPerHeadPerThread
        + laneIdx         * HeadsNumPerWarpSMEM * elementNumPerHeadPerThread
        + bufferIdx       * elementNumPerHeadPerThread
        + elementIdx

    两种 layout 的 bank conflict 差别可以用一个简化模型看出来。假设 shared memory 有
    32 个 bank，bank 宽度按 4B 估算：

      bank = (byte_address / 4) % 32

    令：

      E = elementNumPerHeadPerThread
      B = sizeof(T_in)
      H = HeadsNumPerWarpSMEM = 2

    其中：

      · E 是一个 lane 在一个 head 内负责的 QKV 元素个数。例如 head_dim=64 时，
        E=head_dim/32=2；head_dim=128 时，E=4；head_dim=256 时，E=8。
      · B 是单个 T_in 元素的字节数。例如 half/bf16 时 B=2B，float 时 B=4B。
      · H 是每个 warp 在 SMEM 中保留的 QKV buffer 数量。双缓冲 current/next 时 H=2。

    如果后续同一个 warp 从 SMEM 读回 QKV 时，每个 lane 读取同一个 buffer 中自己负责的
    同一相对 elementIdx，那么相邻 lane 的地址间隔分别是：

      [warp][lane][buffer][element]:
        lane_stride_bytes = H * E * B
        bank_stride       = H * E * B / 4

      [warp][buffer][lane][element]:
        lane_stride_bytes = E * B
        bank_stride       = E * B / 4

    因为第一种 layout 的 lane stride 多乘了 H，也就是把双缓冲维度夹在 lane 和 element
    之间，所以 bank stride 被额外放大。以 H=2 为例：

      half/bf16, head_dim=64:
        E = 2, B = 2
        [warp][lane][buffer][element]  bank_stride = 2, 约 2-way conflict
        [warp][buffer][lane][element]  bank_stride = 1, 通常不冲突

      half/bf16, head_dim=128:
        E = 4, B = 2
        [warp][lane][buffer][element]  bank_stride = 4, 约 4-way conflict
        [warp][buffer][lane][element]  bank_stride = 2, 约 2-way conflict

      float, head_dim=64:
        E = 2, B = 4
        [warp][lane][buffer][element]  bank_stride = 4, 约 4-way conflict
        [warp][buffer][lane][element]  bank_stride = 2, 约 2-way conflict

    因此方案 2 推荐：

      [warp][buffer][lane][element]

    它不能保证所有 dtype/head_dim 都完全没有 bank conflict，但比
    [warp][lane][buffer][element] 少一个 HeadsNumPerWarpSMEM 倍数，通常更适合“每个 lane
    消费自己搬入的连续 QKV 片段”的读回模式。

    注意：cp.async 写入 shared 的阶段不是主要按普通 st.shared bank conflict 来判断。
    需要重点分析的是后续 compute 阶段从 QKV SMEM 读回寄存器的 ld.shared 模式。SMEM
    layout 的主要价值也是为了让后续读取更顺，而不仅是为了让 cp.async 目标地址规整。

  优点：

    · cos/sin 和 q/k weight 都没有 SMEM -> register 中转。
    · dynamic SMEM 只需要 QKV 双缓冲，SMEM 占用更低。
    · 同步更简单，不需要为 cos/sin/q/k weight 单独安排 cp.async group。

  代价：

    · cos/sin 和 q/k weight 都要跨整个 head 循环保持 live，寄存器压力最高。
    · cos/sin/q/k weight 不能用 cp.async 直接搬到寄存器；这些同步 load 的延迟主要依赖
      cache 命中和硬件 warp 调度隐藏。
    · 如果寄存器占用导致 occupancy 下降或 spill，省掉的 SMEM 读取可能不够抵消损失。

  适用倾向：

    · elementNumPerHeadPerThread 较小。
    · rotary_dim/head_dim 较小。
    · 编译后寄存器数可控，没有 spill。
    · profiling 显示 cos/sin/q/k weight load 不是主要瓶颈。


--------------------------------------------------------------------------------
  方案 3：QKV 双缓冲 + cos/sin SMEM + q_weight/k_weight SMEM
--------------------------------------------------------------------------------

  数据路径：

    QKV               global -> qkv_buf0/qkv_buf1 -> register
    cos/sin           global -> per-warp SMEM -> register
    q_weight/k_weight global -> per-warp 或 block-level SMEM -> register

  这个方案把小的只读参数也纳入 cp.async/SMEM 路径。它的目标不是减少最终寄存器使用为 0，
  因为计算时仍然要读进寄存器；它真正想减少的是 q/k weight 和 cos/sin 在整个 head 循环
  中长期占用寄存器的 live range。

  伪代码形态：

    cp_async_qkv_head(0, qkv_buf0);
    cp_async_commit_group();  // group0: head0 QKV

    cp_async_qk_weight_to_smem(this_warp_qk_weight);
    cp_async_commit_group();  // group1: q/k weight

    cp_async_cos_sin_to_smem(this_warp_cos_sin, tokenIdx);
    cp_async_commit_group();  // group2: cos/sin

    // 允许最新的 cos/sin 仍在途，但 head0 QKV 和 q/k weight 必须完成，
    // 因为 RMSNorm 马上要用它们。
    cp_async_wait_group<1>();
    __syncwarp();

    for (uint k = 0; k < headNumInWarp; ++k) {
      uint next = k + 1;

      if (next < headNumInWarp) {
        cp_async_qkv_head(next, (next & 1) ? qkv_buf1 : qkv_buf0);
        cp_async_commit_group();
      }

      vec_T qkv_vec = load_qkv_from_smem((k & 1) ? qkv_buf1 : qkv_buf0);

      // q/k weight 不长期放寄存器，而是本 head 计算前从 SMEM 短生命周期读入。
      float q_w[elementNumPerHeadPerThread];
      float k_w[elementNumPerHeadPerThread];
      load_qk_weight_from_smem(this_warp_qk_weight, q_w, k_w);

      compute_qknorm(qkv_vec, q_w, k_w, elements);

      if (k == 0) {
        if (next < headNumInWarp) {
          cp_async_wait_group<1>();  // 等较老的 cos/sin，允许最新 next QKV 仍在途。
        } else {
          cp_async_wait_group<0>();
        }
        __syncwarp();
      }

      apply_rope_from_smem_cos_sin(elements, cos_smem, sin_smem);
      store_back_qkv(k, elements);

      if (next < headNumInWarp) {
        cp_async_wait_group<0>();
        __syncwarp();
      }
    }

  优点：

    · q/k weight 和 cos/sin 都不需要作为长生命周期寄存器跨整个 head 循环保存。
    · q/k weight、cos/sin 的 global load 可以用 cp.async 组织进 warmup。
    · 如果寄存器压力是主要瓶颈，可能比方案 1/2 更容易维持 occupancy。

  代价：

    · q/k weight 每个 head 使用时要从 SMEM 读入短生命周期寄存器。
    · SMEM 占用最大：QKV 双缓冲 + cos/sin + q/k weight。
    · group/wait 更复杂，容易因为顺序错误导致等待不充分或失去重叠。
    · q/k weight 如果本来能很好命中 read-only/L1/L2 cache，放 SMEM 未必更快。

  注意：

    如果把 q/k weight 先 cp.async 到 SMEM，然后又在 head 循环前一次性读回寄存器并
    长期保存，那么它会同时付出 SMEM 中转和长期寄存器占用。这只是“异步预取 q/k weight”
    的变体，不是本节定义的方案 3。它也可以 benchmark，但不应默认认为更优。

    上面伪代码默认 q/k weight 是 per-warp SMEM，所以 wait 后使用 __syncwarp() 即可。
    如果改成 block-level SMEM，让整个 block 合作加载 q/k weight，则必须保证 block 内
    所有线程都会到达同一个 __syncthreads()，不能让部分 warp 提前 return 后再进入
    block barrier。


--------------------------------------------------------------------------------
  现有 vLLM 融合算子对应哪种方案
--------------------------------------------------------------------------------

  以本项目引入/改写的 vLLM/TensorRT-LLM 风格实现为例：

    src/inference/fused_qknorm_rope_kernel.cu

  里面有两类相关 kernel。

  1. fusedQKNormRopeKernel：一 warp 一个 head 的 baseline

     数据路径是：

       QKV               global/read-only cache -> register
       q_weight/k_weight global/read-only cache -> register
       cos/sin           global/read-only cache -> register

     代码特征：

       · QKV 直接向量化读入 vec_T，再转成 elements[] 寄存器数组。
       · q_weight/k_weight 在 RMSNorm 阶段按 dim 直接从 global/read-only cache 读取。
       · cos/sin 在 RoPE 阶段通过 VLLM_LDG(cos_ptr + half_dim) /
         VLLM_LDG(sin_ptr + half_dim) 直接读到寄存器。
       · 没有 QKV SMEM、没有 cos/sin SMEM，也没有 cp.async 流水。

     所以它不属于上面的方案 1/2/3，而是正确性/简单实现 baseline。

  2. fusedQKNormRopeKernelNTokenHeads：一个 warp 处理同 token 的多个 heads

     这个版本的路径是：

       QKV               global -> per-warp QKV SMEM -> register
       cos/sin           global -> per-warp SMEM -> register
       q_weight/k_weight global/read-only cache -> register

     代码特征：

       · dynamic SMEM 被切成两段：

           [cos/sin per warp][QKV tiles per warp]

       · group0：先把本 warp 负责的所有 head 的 QKV 用 cp.async 搬到 QKV SMEM。
       · group1：再把当前 token 的 cos/sin 用 cp.async 搬到 cos/sin SMEM。
       · cp_async_wait_group<1>()：等待较老的 group0(QKV)，允许较新的 group1(cos/sin)
         继续在途。
       · 随后先做第一个 head 的 QK RMSNorm，用这段计算覆盖一部分 cos/sin 加载延迟。
       · 第一个 head 进入 RoPE 前再 cp_async_wait_group<0>()，保证 cos/sin 已经到位。
       · q_weight/k_weight 在 head 循环前预加载到 q_w/k_w 寄存器，并跨多个 head 复用。

     因此它最接近本文的方案 1：

       QKV SMEM
       cos/sin SMEM
       q_weight/k_weight 寄存器

     但它不是严格意义上的“逐 head QKV 双缓冲 next/current”版本。它当前更像方案 1 的
     批量预取变体：

       · 本文方案 1 的理想形态：
           预取 head0 QKV；
           计算 head0 时预取 head1 QKV；
           计算 head1 时预取 head2 QKV；
           ...

       · 现有 fusedQKNormRopeKernelNTokenHeads：
           先把本 warp 负责的多个 head 的 QKV 一批 cp.async 到 SMEM；
           wait_group<1> 后再依次从 SMEM 读取各 head 做 RMSNorm/RoPE。

     所以更精确的归类是：

       现有 vLLM 多 head/warp 融合算子 =
         方案 1 的当前实现变体
         = QKV 批量 cp.async 到 SMEM + cos/sin cp.async 到 SMEM + q/k weight 寄存器

     它已经利用了“QKV group 先完成，cos/sin group 继续在途，第一个 head RMSNorm 覆盖
     cos/sin 延迟”这一层重叠；但还没有实现“next head QKV 预取和 current head 计算”
     的逐 head 双缓冲流水。

     换句话说，现有 vLLM 多 head/warp 版本的重叠主要发生在第一个 head：

       1. QKV group0 先完成。
       2. cos/sin group1 允许继续在途。
       3. 第一个 head 先做 RMSNorm，因为 RMSNorm 只需要 QKV 和 q/k weight。
       4. 第一个 head 进入 RoPE 前 wait_group<0>()，等 cos/sin 完成。
       5. 再用 SMEM 里的 cos/sin 计算 RoPE。

     对后续 head 来说，QKV 已经在前面一批搬进 QKV SMEM，cos/sin 也已经在第一个
     head RoPE 前等待完成，q/k weight 已经在寄存器。因此后续 head 主要是：

       QKV SMEM -> register
       RMSNorm
       cos/sin SMEM -> register
       RoPE
       store

     后续 head 没有继续形成：

       预取 head k+1 的 QKV
       同时计算 head k

     这种逐 head 双缓冲重叠。如果要让后续 head 也持续重叠，就需要把 QKV 预取改成
     qkv_buf0/qkv_buf1 轮换：

       prefetch head0 QKV
       prefetch cos/sin
       wait head0 QKV
       prefetch head1 QKV while compute head0
       wait head1 QKV
       prefetch head2 QKV while compute head1
       ...


--------------------------------------------------------------------------------
  正确性 baseline：仍然应该先做
--------------------------------------------------------------------------------

  三个方案都比最直接版本复杂。功能验证时仍然建议先保留一个 baseline：

    q_weight/k_weight global/read-only cache -> register
    QKV global/read-only cache -> register
    cos/sin global/read-only cache -> register

  它不追求最终性能，主要用于验证：

    · token/head/dim 索引。
    · Q/K head 判断。
    · RMSNorm 结果。
    · RoPE 结果。
    · 写回位置。

  baseline 正确后，再比较方案 1/2/3。


================================================================================
四、推荐的执行流水
================================================================================

  本节只按上面三个方案组织 one-warp-N-heads 的执行流水。核心结论是：

    不要预设 q_weight/k_weight 一定该进寄存器、cos/sin 一定该进 SMEM。
    它们的不同加载方式应该作为 benchmark 维度。

  推荐实现顺序：

    1. 先做正确性 baseline：所有数据直接 global/read-only cache -> register。
    2. 实现公共的 QKV 双缓冲 cp.async 框架。
    3. 在同一套 QKV 双缓冲框架下比较方案 1、方案 2、方案 3。
    4. 用 profiling 决定最终选择，而不是用静态经验直接定案。

--------------------------------------------------------------------------------
  方案 1 执行流水
--------------------------------------------------------------------------------

  数据路径：

    QKV               global -> qkv_buf0/qkv_buf1 -> register
    cos/sin           global -> per-warp SMEM -> register
    q_weight/k_weight global/read-only cache -> register

  执行顺序：

    1. 计算 tokenIdx、firstHeadIdx、headNumInWarp。
    2. 预取 head0 QKV 到 qkv_buf0，commit。
    3. 预取 cos/sin 到 this_warp_cos_sin，commit。
    4. 加载 q_weight/k_weight 到寄存器 q_w/k_w。
    5. wait_group<1>，保证 head0 QKV 到位，允许 cos/sin 继续在途。
    6. 对每个 head：
       · 预取 next QKV 到另一个 qkv buffer。
       · 从 current QKV buffer 读到寄存器。
       · 用 q_w/k_w 计算 QK RMSNorm。
       · 第一个 head 进入 RoPE 前等待 cos/sin 到位。
       · 从 cos/sin SMEM 读出并做 RoPE。
       · 写回 qkv。

  主要观察指标：

    · cos/sin cp.async 是否被 RMSNorm 和 next QKV 预取有效覆盖。
    · q_w/k_w 长生命周期寄存器是否导致寄存器数过高。
    · cos/sin SMEM 读取和 SMEM 占用是否可接受。


--------------------------------------------------------------------------------
  方案 2 执行流水
--------------------------------------------------------------------------------

  数据路径：

    QKV               global -> qkv_buf0/qkv_buf1 -> register
    cos/sin           global/read-only cache -> register
    q_weight/k_weight global/read-only cache -> register

  执行顺序：

    1. 计算 tokenIdx、firstHeadIdx、headNumInWarp。
    2. head 循环外加载当前 token 的 cos/sin 到寄存器 elementCos/elementSin。
    3. head 循环外加载 q_weight/k_weight 到寄存器 elementQWeight/elementKWeight。
    4. 预取 head0 QKV 到 qkv_channel0，commit。
    5. 对每个 head k：
       · wait_group<0>，保证 current head 的 QKV 已经到达 current channel。
       · currentHead = firstHeadIdx + k，currentIsQ = currentHead < num_heads_q。
       · 如果 k+1 < headNumInWarp，预取 next head QKV 到 nextChannel=(k+1)%2，commit。
       · 从 currentChannel=k%2 的 QKV buffer 读到寄存器。
       · 用 currentIsQ 选择 elementQWeight/elementKWeight 计算 QK RMSNorm。
       · 用 elementCos/elementSin 做 RoPE。
       · 普通 global store 写回 current head。

  注意：

    · next head 的 QKV 预取应该使用 nextChannel=(k+1)%2；current head 读取使用
      currentChannel=k%2。二者不能混用。
    · currentIsQ 必须按 currentHead 计算，不能被 next head 的 isQ 覆盖，否则跨 Q/K
      边界时会选错 q_weight/k_weight。
    · 当前实现每个 lane 只消费自己写入的 SMEM 片段，通常不需要 __syncwarp()；如果改成
      跨 lane 共享 SMEM tile，则 wait_group 后还需要 warp/block 级同步。
    · 写回 current head 是普通 global store，不需要等待 next head 预取完成。下一轮开头的
      wait_group<0> 负责保证 next head QKV 到位。

  主要观察指标：

    · 寄存器数是否明显增加。
    · 是否出现 spill。
    · 少掉 cos/sin SMEM 读写后，执行时间是否下降。
    · cos/sin 同步 load 是否被 cache/warp 调度隐藏。


--------------------------------------------------------------------------------
  方案 3 执行流水
--------------------------------------------------------------------------------

  数据路径：

    QKV               global -> qkv_buf0/qkv_buf1 -> register
    cos/sin           global -> per-warp SMEM -> register
    q_weight/k_weight global -> per-warp 或 block-level SMEM -> register

  执行顺序：

    1. 计算 tokenIdx、firstHeadIdx、headNumInWarp。
    2. 预取 head0 QKV 到 qkv_buf0，commit。
    3. 预取 q_weight/k_weight 到 q/k weight SMEM，commit。
    4. 预取 cos/sin 到 this_warp_cos_sin，commit。
    5. wait_group<1>，保证 head0 QKV 和 q/k weight 到位，允许 cos/sin 继续在途。
    6. 对每个 head：
       · 预取 next QKV 到另一个 qkv buffer。
       · 从 current QKV buffer 读到寄存器。
       · 从 q/k weight SMEM 短生命周期读到寄存器。
       · 计算 QK RMSNorm。
       · 第一个 head 进入 RoPE 前等待 cos/sin 到位。
       · 从 cos/sin SMEM 读出并做 RoPE。
       · 写回 qkv。

  主要观察指标：

    · 寄存器数是否低于方案 1/2。
    · 额外 SMEM 是否降低 occupancy。
    · q/k weight 每个 head 从 SMEM 读取的成本是否明显。
    · group/wait 安排是否真的保留了重叠，而不是退化成全部 wait 后再计算。


--------------------------------------------------------------------------------
  选择建议
--------------------------------------------------------------------------------

  方案 2 可能更优的情况：

    · elementNumPerHeadPerThread 小。
    · rotary_dim/head_dim 小。
    · 寄存器数没有导致 occupancy 明显下降，也没有 spill。
    · cos/sin/q/k weight 的 cache 命中较好。
    · 希望减少 SMEM 占用和 SMEM 读写。

  方案 1 可能更优的情况：

    · cos/sin 寄存器 live range 造成压力，但 q/k weight 寄存器仍可接受。
    · cos/sin load latency 能被第一个 head RMSNorm 和 next QKV 预取覆盖。
    · per-warp cos/sin SMEM 占用不大。
    · q/k weight 放 SMEM 后没有明显收益。

  方案 3 可能更优的情况：

    · q/k weight + cos/sin 同时长期放寄存器导致寄存器数过高。
    · 降低寄存器 live range 能提升 occupancy 或避免 spill。
    · 额外 SMEM 占用不会压低常驻 block/warp。
    · SMEM bank conflict 可控。
    · cp.async warmup 能把 q/k weight 和 cos/sin 的加载隐藏掉。

  不推荐作为最终性能版本的路径：

    QKV global -> QKV SMEM -> register

  但发起 QKV cp.async 后立刻 wait，随后再计算。这只能验证 QKV cp.async 地址切分和同步，
  没有形成“加载 next，计算 current”的流水，还多了一次 SMEM -> register。


--------------------------------------------------------------------------------
  补充：软件流水线与硬件 warp 调度的关系
--------------------------------------------------------------------------------

  上面方案 1/2/3 里的“流水线并行”，和 GPU 硬件的 warp 调度隐藏延迟是同一个大思路：

    在等待内存时，不让执行资源闲着。

  但它们属于两个层级：

    1. 硬件 warp 调度

       当某个 warp 因 global memory load 等待时，SM 可以切换去执行其他 ready warp。
       这是 GPU 硬件自动完成的延迟隐藏方式。

       形态：

         warp A 等内存
         SM 调度 warp B 执行
         SM 调度 warp C 执行

    2. 软件流水线 / cp.async 流水

       这是 kernel 代码显式组织出来的。当前 warp 在计算 current head 时，提前发起
       next 数据的异步拷贝，让数据搬运和计算在时间上重叠。

       形态：

         cp.async next -> smem
         compute current
         wait next

  在本文三个方案里：

    · 方案 1：
      QKV 双缓冲让 next head QKV 预取和 current head 计算重叠；cos/sin async load
      也可以和第一个 head 的 QK RMSNorm 重叠。

    · 方案 2：
      QKV 双缓冲仍然成立；cos/sin 和 q/k weight 直接进寄存器，不能用 cp.async
      直接搬到寄存器，因此这部分 load 主要依赖 cache 命中和硬件 warp 调度隐藏。

    · 方案 3：
      QKV 双缓冲仍然成立；cos/sin 和 q/k weight 也进入 SMEM warmup，可以用 cp.async
      组织加载，但要付出更多 SMEM 占用和 SMEM -> register 读取成本。

  两者可以同时存在：

    · active warps 足够多时，硬件 warp 调度可以在 warp 间隐藏延迟。
    · 同一个 warp 内又可以通过 cp.async 软件流水隐藏当前 warp 自己的数据加载延迟。

  因此 cp.async 流水不是替代 occupancy，而是和 occupancy 一起工作。SMEM 占用过高导致
  active warps 下降时，硬件 warp 调度隐藏延迟的能力会变弱；这时软件流水能帮忙，但不一定
  能完全弥补 occupancy 下降。


================================================================================
五、一个 block 处理一个 token 的替代流水
================================================================================

  除了“一个 warp 处理同一个 token 的 N 个 heads”之外，还可以设计成：

    一个 block 负责一个 token
    block 内多个 warp 共同处理这个 token 的所有 Q/K heads

  这种映射下，block 内所有 warp 都属于同一个 token，因此 cos/sin 可以放成 block 级
  共享的一份，而不是每个 warp 各放一份：

    cos/sin global -> block-level SMEM -> block 内所有 warp 复用

  q_weight/k_weight 也可以放到 block 级 static/dynamic SMEM 中：

    q_weight/k_weight global -> block-level SMEM -> register

  然后每个线程或每个 warp 仍然加载自己负责的 QKV 到寄存器计算：

    QKV global -> register -> QK RMSNorm -> RoPE -> store

  伪代码形态：

    extern __shared__ char smem[];

    T_cache* cos_smem = reinterpret_cast<T_cache*>(smem);
    T_cache* sin_smem = cos_smem + rotary_dim / 2;
    float* q_w_smem = reinterpret_cast<float*>(sin_smem + rotary_dim / 2);
    float* k_w_smem = q_w_smem + head_dim;

    // block 内线程合作加载当前 token 的 cos/sin。
    for (uint dim = threadIdx.x; dim < rotary_dim / 2; dim += blockDim.x) {
      cos_smem[dim] = cos[tokenIdx * (rotary_dim / 2) + dim];
      sin_smem[dim] = sin[tokenIdx * (rotary_dim / 2) + dim];
    }

    // 可选：block 内线程合作加载 q/k weight。
    for (uint dim = threadIdx.x; dim < head_dim; dim += blockDim.x) {
      q_w_smem[dim] = convert(q_weight[dim]);
      k_w_smem[dim] = convert(k_weight[dim]);
    }

    __syncthreads();

    // block 内每个 warp 处理一个或多个 head。
    for (uint localHead = warpIdxPerBlock; localHead < qkHeadsPerToken;
         localHead += warpsPerBlock) {
      vec_T qkv_vec = load_qkv_to_register(tokenIdx, localHead, laneIdx);
      compute_qknorm(qkv_vec, q_w_smem, k_w_smem, elements);
      apply_rope_from_block_smem(elements, cos_smem, sin_smem);
      store_back_qkv(tokenIdx, localHead, elements);
    }

  这种方案的优势：

    · 同一个 token 的 cos/sin 在 block 内只加载一份，所有 warp 复用。
    · q_weight/k_weight 如果放入 SMEM，也可以 block 内所有 warp 复用。
    · 同步逻辑更直观：block 开头加载共享数据，__syncthreads() 后统一使用。

  这种方案的代价：

    · block 粒度变成 token 时，grid 里的 block 数通常约等于 num_tokens。CUDA 调度的基本
      常驻单位是 block；同一个 block 内的多个 warp 会驻留在同一个 SM 上，不能把这个
      token 的不同 head chunks 分散到多个 SM。
    · one-warp-N-heads 的工作粒度更细：
        totalWarps = num_tokens * ceil(qkHeadsPerToken / headsPerWarp)
      这些 global warps 会再打包成多个 block，因此即使 num_tokens 较小，只要每个 token
      的 Q/K heads 足够多，也仍然可能产生更多 block，分发到更多 SM。
    · 如果 num_tokens 和 Q/K heads 都很少，两种方案都会缺少足够并行工作；但如果
      num_tokens 小、heads 多，one-block-one-token 更容易把同一 token 的 head 并行度限制
      在单个 block/单个 SM 内。
    · block 级 SMEM 放 cos/sin + q/k weight 会增加 shared memory 占用，可能降低 occupancy。
    · 需要 block 级 __syncthreads()，必须保证 block 内所有线程都走到同一个 barrier。
    · q_weight/k_weight 本身是只读小数组，放 SMEM 未必比寄存器预加载更快。

  SMEM 占用影响 occupancy 的含义：

    GPU 每个 SM 的 shared memory 容量是有限的。一个 block 使用的 SMEM 越多，同一个 SM
    上能同时驻留的 block 数可能越少；常驻 block 少了，常驻 warp 也可能减少，隐藏访存
    延迟的能力就可能下降。

  例如假设一个 SM 可用 100 KB shared memory：

    每个 block 使用 10 KB SMEM -> 理论上最多 10 个 block/SM
    每个 block 使用 40 KB SMEM -> 理论上最多  2 个 block/SM

  实际 occupancy 还会同时受寄存器数量、最大 block 数、最大 warp 数、线程数等限制，但
  SMEM 是其中一个硬约束。

  one-block-one-token 里如果把 cos/sin 和 q/k weight 都放进 block 级 SMEM，大致占用是：

    cos/sin bytes =
        rotary_dim * sizeof(T_cache)

    q/k weight bytes =
        2 * head_dim * sizeof(float)

    total block-level cache bytes =
        cos/sin bytes + q/k weight bytes

  例子：

    rotary_dim = 128, T_cache = half
    cos/sin bytes = 128 * 2 = 256 B

    head_dim = 128
    q/k weight bytes = 2 * 128 * 4 = 1024 B

  在这里讨论的 one-block-one-token 基础方案中，QKV 仍然是直接加载到寄存器，不默认占用
  SMEM。因此默认 block-level SMEM 成本主要就是 cos/sin 和可选的 q/k weight。

  单看这个例子，cos/sin + q/k weight 的 SMEM 并不大，未必会影响 occupancy。只有在后续
  又额外加入其他 SMEM 缓冲，例如某种 QKV tile、双缓冲或更多临时空间时，per-block SMEM
  才可能继续增加并限制每个 SM 的常驻 block 数。

  所以这里不是说 block 级 SMEM 一定更慢，而是：

    shared memory 用量增加
      -> 每个 SM 可同时驻留的 block/warp 可能减少
      -> 隐藏访存延迟的能力可能下降
      -> occupancy 可能下降

  这也是 q/k weight 是否放入 block-level SMEM 需要 benchmark 的原因：它们小、只读、
  可缓存，优先占用 SMEM 未必能换来收益；但如果寄存器压力或重复读取成为瓶颈，
  block-level SMEM 也可能值得尝试。

  和 one-warp-N-heads 的取舍：

    · one-warp-N-heads：
      调度粒度更细，可以把同一 token 的不同 head chunks 分发到多个 block/SM；代价是
      cos/sin 可能被同一 token 的多个 warp 重复加载，q/k weight 也会被多个 warp 重复
      加载。二者具体谁更值得缓存到 SMEM，取决于 rotary_dim、head_dim、寄存器压力、
      cache 命中和 SMEM 占用，不能只靠静态规则判断。

    · one-block-one-token：
      cos/sin 复用更充分；但同一 token 的 head 工作被限制在一个 block 内，block 粒度更粗，
      可能牺牲跨 SM 并行度和 occupancy。

  因此 one-block-one-token 是一个可行算法分支，不是绝对更优。是否更快取决于
  num_tokens、num_heads_q/k、head_dim、rotary_dim、dtype、blockSize、SMEM 占用和实际
  GPU 架构。最终需要 benchmark 对比。

  总体判断：

    · one-block-one-token 是粗粒度映射。
      数据复用更充分，但对输入形状更敏感：num_tokens、num_heads_q/k、blockSize、
      head_dim、rotary_dim、SMEM 占用都会明显影响并行度和 occupancy。

    · one-warp-N-heads 是细粒度映射。
      数据复用差一些，会有 cos/sin 和 q/k weight 的重复加载；但工作拆得更细，对不同
      batch/token/head 组合更鲁棒，也更容易把并行度铺到多个 SM 上。

  所以 one-block-one-token 更像针对特定形状做深度优化的版本；one-warp-N-heads 更适合
  作为通用 baseline 或更稳妥的默认实现。



================================================================================
六、常见错误
================================================================================

  错误 1：所有 warp 都写 dynamicSmem[0]

    char* smem_dst = &dynamicSmem[0];

  这样不同 warp、不同数据区域会互相覆盖。必须先按数据类型切段，再按 warpIdxPerBlock
  切出每个 warp 的私有区域；如果启用 QKV SMEM，还要继续按 head 或双缓冲 buffer 切分。


  错误 2：把 cos/sin 做成 block 级唯一一份

  当前映射下，一个 block 内不同 warp 可能处理不同 token。不同 token 的 cos/sin 不同。
  因此至少应该每个 warp 一份，或者重新设计 grid/block 映射，让一个 block 只处理一个 token。


  错误 3：在部分线程 return 后使用 __syncthreads()

    if (tokenIdx >= num_tokens) return;
    __syncthreads();  // 危险

  如果同一个 block 里只有部分 warp 越界 return，其余线程进入 barrier，会造成 barrier
  不匹配。需要把 block 级同步放到所有线程一致执行的路径上。


  错误 4：把 cp.async.wait_group 当成线程间同步

  cp.async.wait_group 等的是当前线程发起的 async copy group，不是等待 block 内其他线程。
  如果后续跨线程共享 SMEM，需要额外使用 __syncwarp() 或 __syncthreads()，取决于共享范围。

    方案 3：
      QKV 双缓冲 SMEM；cos/sin SMEM；q/k weight SMEM。
